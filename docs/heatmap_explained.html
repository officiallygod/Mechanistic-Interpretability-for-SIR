How a feature heatmap is made

From one camera frame to a map that shows where a single SAE feature fires, and which object it belongs to. ResNet runs forward only once. The heatmap is read straight from the sparse codes; nothing is sent back through the network.

Toy data: the scene and all activations are invented for illustration, not results.

01

Camera frame

RoboCasa renders each camera at 128×128 px. SIR feeds this frame to ResNet-18 as it is.

image: 3 × 128 × 128

The simulator also knows where every object is. We use those boxes later, only to label features.

Toy scene: drawer with handle, mug, microwave, gripper
02

ResNet-18 forward, stop at layer 4

The image passes through ResNet once. Convolutions keep the layout, so layer 4 is a small grid laid over the image: each cell sits over one patch.

layer 4: 512 × 4 × 4 = 16 cells

Every cell holds a dense 512-d vector: almost every channel is non-zero, and one channel mixes many concepts. Click a cell to inspect it.

cell (row 2, col 1): 512 channels, dense
03

SAE encoder on every cell

The SAE turns each cell's 512 numbers into 4,096 features, of which only 32 may be non-zero (Top-32). Ideally each feature means one thing.

x ∈ ℝ⁵¹² → f ∈ ℝ⁴⁰⁹⁶, 32 active
f = TopK₃₂( ReLU( W_enc (x − b_dec) + b_enc ) )

The orange bar is the feature selected above. Its height in this cell is one pixel of the heatmap.

04

Collect feature j from every cell

Repeat step 03 for all cells and keep only feature j. The result is a tiny map at layer-4 resolution: the heatmap before any upsampling.

f[j] over the grid: 4 × 4

This is all the location information the feature carries. Everything after this step only changes how it is displayed.

Activation of the selected feature in each cell
05

Upsample to image size

Bilinear interpolation stretches the grid to 128×128 px so it can be laid over the frame, as in src/grounding.py:

H_j = F.interpolate(f[j], size=(128, 128), mode="bilinear", align_corners=False)

The map now looks smooth, but it holds no new detail: it is still the same 16 (or 49) numbers.

Upsampled heatmap H_j over the frame
06

Compare with the object boxes

Two ways to say which object the feature belongs to:

IoU: keep pixels above the threshold, then measure overlap with each box. The portal labels a feature when IoU > 0.5.

Activation share: the part of the total heatmap that falls inside each box. No threshold needed.

ObjectIoUShare

What this toy shows

  • Coarse location only. At 4×4 one cell spans 32×32 px, so a small part like the handle cannot get its own blob. The handle feature ends up overlapping the whole drawer more than the handle.
  • 7×7 helps, but costs. At 7×7 the handle blob sits on the handle (try this view). But the policy was trained on 128 px frames, so upscaling feeds it an input size it never saw.
  • Neither rule is safe at 4×4. The mug feature reaches IoU 0.22 with the mug, and by activation share it even points to the microwave (see it), because the blob spills over both.
  • Parts sit inside their object. Every handle pixel is also a drawer pixel, so the drawer always collects at least as much activation share as its handle. To tell part from whole, a rule has to account for that, for example by dividing the share by the box area.
  • Features without an object exist. The texture feature passes no IoU cutoff and spreads its share thinly. That is the correct outcome: it should not join the latent kept set.
  • Need pixel detail? Then we would go back through ResNet: gradient attribution (e.g. Grad-CAM, integrated gradients) of f_j with respect to the input pixels gives finer but noisier maps.
